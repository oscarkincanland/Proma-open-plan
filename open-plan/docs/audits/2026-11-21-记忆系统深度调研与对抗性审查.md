## 0. 结论摘要

**一句话定位**：这套系统本质是「工作区 Markdown 文件 + 全局人工审批队列 + 每轮关键词召回」，是一套**治理原型**，还不是业界主流的「抽取 → 合并/失效 → 检索 → 注入 → 淘汰」记忆运行时。它的治理链（准入、审批、受保护目标、审计事件）比多数开源方案更严，但**读写闭环没有闭合**：写得进、审得慢、读得少、记不实。更关键的是，下面列出的多数问题在 2026-09-17 的计划里已经逐条写明并给了验收口径，两个多月后仍未落地（§5.0「计划债」）。

**核心结论（按严重度排序）**：

1. **真正的记忆上限不是 1500 字符，而是动态上下文段的 6000 字节。** 当前工作区实测：动态上下文 5669 字节，其中固定前缀 3783、记忆块 1886，**只剩 331 字节（约 110 个汉字）**；再增加约 2–3 条记忆，尾部就会被 `section()` 从头截掉（`上下文段落.mjs:33,44-52`），而记忆恰好排在动态上下文的最后一行（`agent.mjs:8243`）。1500 字符切片是第二道、更松的闸；60KB 召回预算（`运行开关.mjs:342`）永远不会到达模型。`memory_recall_selected.injectedBytes` 是组装量；今天的 1810 字节恰好还没被切，一旦触发段预算截断，事件仍可能报 `truncated=false`（M-03/M-04）。
2. **自动抽取绕过了全部准入规则，也无视项目「仅手动维护」策略。** `memory_update` 工具会先跑 `evaluateMemoryCandidate` 并检查 `memoryPolicy`（`agent.mjs:5374-5396`），但收尾自动抽取直接 `createMemoryProposal`（`server/执行句柄.mjs:374-389`），敏感信息、临时环境、Harness 内部实现、重复内容都不拦，`manual` 项目照样产候选。R14「敏感信息不进入记忆」的验收口径因此不成立。
3. **候选队列只进不出，而且测试在污染真实队列。** 现场：审计开始时 113 条候选，104 条 pending（中位年龄 18 天，44 条超 30 天），9 条 approved；跑完 `test:memory-metadata` 后变为 **114 条 / 104 pending / 10 approved**——新增的那一条正是测试产生、状态 approved。10 条 approved 中 **7 条来自 `%TEMP%\oaw-mem-*` 测试工作区**，真实工作区只有 3 条。根因之一是 `scripts/记忆元数据测试.mjs:118-150` 没有隔离 `OAW_MEMORY_PROPOSALS_FILE`，每次跑测试都往真实库追加；配合 300 条 FIFO 静默淘汰（`记忆管理.mjs:14,76-78`），`npm run verify` 会慢慢把用户真实候选挤掉——这是**可复现的数据丢失路径**。
4. **分层摘要路径还有 1800/2800 两层静默截断，叠加上面的段预算与 1500 切片就是四道闸。** 非召回路径每个 `memory/*.md` 只读前 1800 字符、总量再切 2800（`agent.mjs:1080-1087,1135`）；召回路径虽读全文，最终仍要过 6000 字节段预算与 1500 字符切片。`MEMORY.md` 是单文件 append-only，**排在后面的分类（通常正是「经验教训」）会先消失**。另外 frontmatter 嵌套 `metadata.type` 解析不出来（实测 `lesson` 文件被归为 `project_fact`），manifest 的描述取到 H1「记忆索引」，选择器拿到的信号基本无效。
5. **记忆的权威位置反了。** 记忆文本被拼进**用户消息**（`agent.mjs:7648-7660`），每轮重复一份并永久留在会话历史；而工作区 `AGENTS.md` 在系统上下文。于是「记忆里的工作规则」比「项目规则」更靠近对话尾部，冲突时存在 recency 压过权威的风险；同时 `agent.mjs:8243` 的标签写「不含规则」，实际 `memCtx` 包含 `## 记忆中的工作规则`（`agent.mjs:1130`），recall 命中时又可能整体替换掉规则层——同一段文本的组成随开关与查询词漂移。
6. **敏感内容会被「拒绝事件」回显并落盘。** `memory_update` 被准入拒绝时，事件携带原文前 120 字（`agent.mjs:5391-5396`）；`memory_proposal_rejected` 在事件注册表里是 `persist: true`（`server/事件注册表.mjs:201`），会经 SSE 回前端并可能进入 `.oaw/runs/*`。API Key/密码片段即使没进记忆，也已经进了事件流与运行日志——直接违反 AGENTS.md §9「不输出密钥/Token」。
7. **准入只在模型工具入口生效，审批链可以绕过。** 面板把候选编辑成 1000 字或含密码（`记忆管理.mjs:199` 用 `cleanText` 上限 1200），或合并多条（`:329`），再点批准，`approveMemoryProposal` 不会重跑 `evaluateMemoryCandidate`（`:286-296`）。所以「6–220 字、敏感信息拦截」不是全链路规则。另有：候选库 JSON 损坏时 `readStoredProposals` 静默返回空（`:67-74`），下一次写入会把整库覆盖成当前一条（§M-23）。

**健康度速评**（10 分制，主观但逐项有证据）：

| 维度 | 分数 | 理由 |
|---|---|---|
| 存储与作用域 | 5 | workspace 单作用域清晰；`scope` 只写不读，`user` scope 名不副实 |
| 写入治理 | 4 | 有审批链/准入/受保护目标；但抽取与审批链可绕过准入、拒绝事件回显原文、候选库损坏即清零 |
| 读取有效性 | 2 | 关键词非语义；6000 字节段预算已只剩 331 字节余量；1500/1800/2800 四重截断，预算记账失真 |
| 生命周期 | 2 | 无 supersede/revoke/TTL/删除；stale 只标注不处理；审批即「今天核验」 |
| 可观测性 | 4 | 事件齐全、UI 有标签；但无健康度面板、无实际注入量、抽取成本归不到父 Run |
| 与 PRD 一致性 | 4 | R14 形式满足；「敏感信息不进入记忆」「不静默写入」被抽取链路与拒绝事件实质破坏 |

## 2. 事实：这套记忆系统长什么样

### 2.1 存储与作用域

- **唯一硬边界是 workspace。** 「项目记忆」= `<workspace>/AGENTS.md` + `<workspace>/memory/`；`projectId` 只是候选的元数据，不是存储分区（`记忆管理.mjs:147-191`）。
- **没有跨项目/用户级 Agent 记忆。** `AGENT_DIR` 只用于加载全局 `AGENTS.md` 规则（`上下文文件.mjs:37-56`），没有 `AGENT_DIR/memory`。
- **没有独立工具记忆。** 工具经验只能写成 `work_rule`/`lesson`；工具错误建议是静态代码。
- **候选队列是全局单文件。** 每条候选自带 `workspace` 字段，读的时候再过滤（`记忆管理.mjs:12-16,135-145`）。

### 2.2 写入链

```
                      ┌─ memory_update 工具（仅 Work）
模型/回合 ────────────┤     ├─ memoryPolicy=manual → 拒绝
                      │     ├─ evaluateMemoryCandidate（6 条硬规则）
                      │     └─ createMemoryProposal → pending
                      │
                      └─ Run 收尾自动抽取（默认开）
                            ├─ shouldExtract（Work + ≥3 字 + 本轮未直接写）
                            ├─ 独立只读子会话（5 轮，read/grep/find/ls）
                            ├─ 严格 JSON 解析（≤220 字）
                            └─ createMemoryProposal → pending   ← 无准入、无 manual 检查

pending ──(用户批准)──> writeMemoryEntry ──> memory/MEMORY.md（带 置信度/核验日期/适用范围）
   │                        └─ acquireWriteLock(kind=memory_approval)
   ├─(拒绝)──> rejected
   └─(合并)──> merged
```

关键事实：
- `MEMORY.md` 是唯一正式落盘位置；写入按 `## 分类` 标题定位，找不到就新建（`记忆管理.mjs:249-266`）。
- 条目格式：`- 内容（置信度 0.7 · 核验 2026-11-19 · 适用 workspace）`，无置信度时省略该字段（`记忆元数据.mjs:48-57`）。
- 普通 `write`/`edit`/`bash` 不能改 `memory/` 与 `AGENTS.md`（`写入协调.mjs:137-145,361-428`；`agent.mjs:1930-1940`）；面板编辑是唯一例外（`index.mjs:6446-6459`）。
- 提案内容上限 1200（`记忆管理.mjs:15`），准入 220，工具描述却说 100 字（`agent.mjs:5337`）——三处口径不一致。

### 2.3 读取链（五条路径）

| # | 路径 | 读取内容 | 预算/截断 | 生效时机 |
|---|---|---|---|---|
| 1 | Pi 原生上下文 | 工作区 `AGENTS.md` + `AGENT_DIR` 全局 `AGENTS.md` + 内置运行宪法 | 无显式预算，整文件 | Runtime 创建；每 30s 后台 reload，但普通对话不重建 system prompt（M-24） |
| 2 | 合成 `.agent-context.md` | 固定规则文本（工作区/当前文件/工具纪律/地图/画布等） | 固定字符串 | Runtime 创建时生成（`agent.mjs:1480-1520`） |
| 3 | 每轮动态上下文 | 工作区绝对路径 + 当前文件 + 项目记忆（或召回结果） | 整段 **6000 字节**（记忆实际只剩约 2.2KB） | 每轮 prompt（`agent.mjs:8178-8247`） |
| 4 | 磁盘 `.agent-context.<thread>.md` | 同 #3 的分层摘要（**不含召回结果**） | 2800 字符 | 每轮写；Pi **不自动加载**，只在模型主动 read 时可见；已积累 56 个/134KB 无清理 |
| 5 | 模型直接 read/grep | `memory/*.md` 原文 | 模型自行决定 | 按需 |

补充：
- 分层摘要（#3/#4）按 `## 规则/偏好/项目/经验` 分桶，每文件先切 1800，再总切 2800（`agent.mjs:1075-1136`）。
- 召回（#3 的替代分支）扫描顶层 `memory/*.md`，用中文 bigram + 英文词打分，最多 12 个文件、单文件 8KB、总量 60KB（`记忆召回.mjs:63-92,98-122,209-239`）。

- 子代理拿不到记忆与工作区规则：`noContextFiles: true` + 自定义 systemPrompt（`agent.mjs:5704-5720`）。

### 2.4 生命周期现状

| 阶段 | 现状 | 缺口 |
|---|---|---|
| candidate | `pending` | 300 条上限 FIFO 淘汰；无 TTL |
| approved | 写入 `MEMORY.md`，`lastVerified`=批准当天 | 未复核却标记新鲜；无 supersede/revoke |
| rejected | 永久保留 | 拒绝原因有记录，但无「不再重复骚扰」的语义去重 |
| merged | 源条目 `merged`，目标内容拼接 | 只允许同工作区同分类 |
| stale | 按 `lastVerified` >90 天在召回时加一行提示 | 不阻断、不派复核任务、不降权 |

## 3. Harness 到底如何读取记忆（逐跳）

把一轮 Work 对话拆开，记忆相关动作只发生在三处：

```
用户输入
  │
  ├─ 1. entry.lastPromptText = text                     （agent.mjs:7585）
  │
  ├─ 2. sharedMemCtx = readMemoryContext(workspace)      （7529）
  │      ├─ 扫 memory/*.md，每文件 ≤1800 字符
  │      └─ 按分类拼成 ≤2800 字符
  │
  ├─ 3. writeContextFile(sharedMemCtx)                   （7530）
  │      └─ 写 .agent-context.<thread>.md（含 2800 记忆；不含召回）
  │
  ├─ 4. dynamicText = buildDynamicContext(sharedMemCtx)   （7592 → 8178）
  │      ├─ if memoryRecall（默认开）:
  │      │     recall = buildRecallContextSync(60KB 预算)  （8190）
  │      │     if (recall.text) memCtx = recall.text       （8195，覆盖分层摘要）
  │      │     发 memory_recall_selected{injectedBytes}    （8198-8204）
  │      └─ 返回 "...项目记忆摘要：\n" + memCtx.slice(0,1500)（8243）
  │
  ├─ 5. text = sections(dynamicText + skills + task + user)（7650-7660）
  │      └─ 记忆进入用户消息文本
  │
  └─ 6. Pi 发请求
```

### 3.1 配置预算 vs 实际注入

| 环节 | 配置值 | 实际进入模型的量 | 证据 |
|---|---|---|---|
| 召回组装 | 60KB / 单文件 8KB / ≤12 文件 | 可能 60KB | `运行开关.mjs:342`、`记忆召回.mjs:162-239` |
| 分层摘要 | 每文件 1800、总 2800（字符） | ≤2800 字符 | `agent.mjs:1080-1135` |
| **dynamic-context 段** | 6000（名为 chars，实为 **bytes**） | **Work 下的实际约束**：当前 5669/6000 字节，记忆只剩约 331 字节 | `上下文段落.mjs:33,44-52`；实测见 §6.2 |
| 记忆切片 | — | ≤1500 字符（Chat 800）；中文通常先被上面的段预算截住，英文才轮到它 | `agent.mjs:8243` |
| 审计事件 | `injectedBytes`、`truncated` | 组装量；不反映段预算截断 | `记忆召回.mjs:220-239` |

结论：**60KB 预算永远不会到达模型**。从松到紧依次是「召回 60KB → 分层 2800 字符 → dynamic 段 6000 字节 → 1500 字符切片」；Work 中文场景下 6000 字节段预算先触发（固定前缀已占 3783 字节），英文场景下 1500 字符切片可能先触发。今天 13 条记忆、491 字符时刚好没触发任何截断；再增长约 2–3 条就会开始静默丢尾部，而事件仍可能显示「未截断」。

更糟的是，这 3783 字节的固定前缀主要是**每轮重复注入的静态工具规则**（Office 纪律、错误码表、Word 批注、计划闸门等），它们已经作为合成 `.agent-context.md` 在系统上下文里存在一份；现在每轮又在用户消息里再带一份，既浪费预算、挤掉记忆，又永久堆积在会话历史里。把静态规则移出 per-turn 动态段，是释放记忆预算最低成本的一步。

### 3.2 哪些记忆根本没进 prompt

1. `memory/` 下的嵌套子目录与 `.txt`：面板能看到（`index.mjs:6284-6296`），召回与分层只读**顶层 `.md`**（`记忆召回.mjs:68`、`agent.mjs:1085`）。
2. 每个文件 1800 字符之后的内容（分层路径）。
3. `MEMORY.md` 2800 字符之后的内容（分层路径）。
4. 召回结果 1500 字符之后的所有内容（最终 prompt）。
5. 未命中关键词的条目/文件（同步召回只做 token 包含）。
6. 子代理：不会**自动**注入记忆或 AGENTS.md（`noContextFiles: true`）；但子代理持有 `read` 工具，能主动读取（`agent.mjs:5731-5744`），所以准确说法是「默认不继承」，不是「无权读取」。
7. 模型不主动 `read` `.agent-context.<thread>.md` 时，2800 字符的「权威版本」不会被看到；prompt 只给了「需要细节时 read」的软提示。Pi 只自动加载 `AGENTS.md`/`CLAUDE.md`（`resource-loader.js:129-130,179-209`），而 `agent.mjs:1481-1521` 注入的 `.agent-context.md` 是**静态字符串**，不是磁盘文件内容——thread 快照默认根本不进 prompt。
8. **快照文件只增不减。** `writeContextFile` 每轮写一份 `.agent-context.<thread>.md` 与兼容文件，没有清理逻辑；当前 `office-workspace` 已有 **56 个**、约 **134KB**（本次实测），含历史记忆摘要，且被产物面板的隐藏文件规则排除。用户删除/修正记忆后，旧副本仍留在工作区。
9. **threadId 直接参与文件名，存在路径穿越。** `path.join(ws, `.agent-context.${entry.threadId}.md`)`（`agent.mjs:8282`）未校验 `..`；实测 `threadId="x/../../evil"` 解析到工作区外的 `evil.md`，而 `atomicWriteFile` 会自动建父目录。API 的 `thread` 来自请求体（`index.mjs:5279`），默认无鉴权（仅本机）。

### 3.3 召回行为的具体怪异点

- **查询为空时注入前 12 个文件。** `selectMemoriesByKeyword` 在无 token 时返回 `manifest.slice(0, limit)`（`记忆召回.mjs:113`）；没有当前文件时，单字提示「好」「嗯」没有 bigram，会触发这一分支——不是「不召回」，而是「把记忆库前 12 个文件都塞进来」。（有当前文件时，`[当前工作文件: X]` 会提供 token，通常不会走空查询分支。）
- **召回 query 不是用户原话。** `agent.mjs:7557-7562` 先把 `[当前工作文件: X]` 前置到 text，`7585` 才写 `entry.lastPromptText`，召回再用它做 query；因此当前文件名（如「OD分析报告.docx」）参与关键词打分，切换当前文件会改变召回结果。
- **`MEMORY.md` 几乎必中。** 文件名大写排序在前，正文参与打分，任何常见交通词（「规划」「项目」「文件」）都能命中；单文件粒度意味着一旦命中就是整文件注入。
- **frontmatter 嵌套类型解析失败（实测）。** `metadata:\n  type: lesson` 不会被 `parseFrontmatter` 识别（只匹配顶格 `key: value`），类型退回文件名推断；`MEMORY.md` 的描述取到 H1「记忆索引」，`lesson` 文件被判为 `project_fact`。选择器（若接线）拿到的类型/描述信号基本无效。
- **`MEMORY.md` 永远是 `project_fact` 标签**，分类信息在 manifest 里丢失。
- **当前实测**：召回文本 750 字符 / 1810 字节；`annotateMemoryBody` 返回 `total=13, stale=13`，标注后 1635 字节（原 1089 字节）——全部条目都被提示「未标注核验时间」。

## 4. 市面 Agent 记忆系统怎么做的

> 以下为公开文档/论文/产品说明的归纳，用于对照设计取舍，不代表对本项目的事实判断。

### 4.1 六种主流范式

| 范式 | 代表 | 载体 | 写入 | 读取 | 生命周期 | 隔离 |
|---|---|---|---|---|---|---|
| 分层指令文件 | Claude Code `CLAUDE.md`、`AGENTS.md`、Cursor rules | 版本库内 Markdown | 人写；`@import` 组合；路径作用域规则按需加载 | 启动加载工作目录及祖先；子目录规则在读写该目录时加载；`MEMORY.md` 索引只加载前 200 行/25KB，主题文件按需 | 人工维护，无自动失效 | managed/user/project/local 四级，近者后读 |
| 文件式自记忆 | Claude Code auto memory | `~/.claude/projects/<project>/memory/` | 模型自动保存偏好/纠正/项目背景；跳过代码可推导内容 | 索引启动加载，主题文件按需 | 用户 `/memory` 查看、可关 | 按 repo，worktree 共享、不跨机器 |
| 抽取型记忆服务 | Mem0 | 向量库（+平台版图记忆） | `add` 抽取事实；查重、去冗、抽实体；更新/删除必须显式 | `search` 多信号排序（语义/关键词/实体/时间），应用决定注入哪些 | add/update/delete；冲突默认加法式，不自动消解 | `user_id`/`agent_id`/`run_id` |
| 时序知识图谱 | Graphiti / Zep | 图数据库 | 以 episode 摄入，抽实体与边，记录有效期，失效旧边 | 时间点查询 + 溯源；混合检索 | 双时态（事件时间/摄入时间），显式失效 | group/namespace |
| 可自编辑核心记忆 | Letta / MemGPT | core memory blocks（在上下文内）+ archival/recall（外置） | Agent 通过记忆工具自编辑，块有大小限制；sleep-time 后台整理 | 核心块常驻；归档按需检索进上下文 | 自编辑 + 后台巩固 | agent/user 级 |
| 热路径/后台 + 命名空间 | LangMem | Store / 自管存储 | 对话中即时形成（热路径）或事后后台形成 | 语义/键值/元数据过滤；manage 工具 | 抽取/更新/合并/删除 | 层级 namespace（org/user/context） |
| 产品化用户控制 | ChatGPT Memory | 保存的记忆 + 引用聊天历史 | 用户显式要求或模型保存；摘要 + 条目 | 每轮选择相关记忆；来源可展示 | 用户查看/纠正/删除/关闭；关闭后 30 天内删除派生记忆 | 账号级；临时聊天不写 |

### 4.2 共性规律

1. **小而常驻 + 大而按需。** 常驻部分都有硬上限（Claude Code 200 行/25KB；Letta core blocks 有块大小限制），细节放外置、按需取。没有主流方案把「全量记忆原文」每轮塞进用户消息。
2. **写入必须有「更新/删除/失效」，不只是追加。** Mem0 的 update/delete、Graphiti 的边失效、ChatGPT 的删除与「不要再提」，都承认记忆会过时、会错、会冲突。纯 append + 人工 ignore 会让库只增不减。
3. **检索是多信号或结构化的，不是单关键词。** 向量、关键词、实体、时间、命名空间过滤；文件式方案则用「索引 + 主题文件 + 路径作用域」降低检索难度。
4. **记忆进入上下文的位置是「系统/开发者提供的背景」，不是用户发言。** 这样权威等级清楚，也不会污染用户原话与缓存。
5. **作用域在写入前就确定。** user/agent/run、org/user/context、managed/user/project/local；读取按作用域过滤，而不是写入后再靠元数据标注。
6. **可观测与可纠正是一等公民。** `/memory`、`/context`、Sources、记忆管理页；用户能看到「它为什么记得这件事」并改掉。
7. **后台形成与热路径形成分开。** 抽取放后台避免拖慢回复；热路径只在用户明确要求时写。两者都有预算/频率控制。

### 4.3 本项目对照

| 能力 | 主流做法 | 本项目 | 差距判断 |
|---|---|---|---|
| 常驻层 | 小索引/核心块，有硬上限 | 单文件 `MEMORY.md` 全量摘要，1500 字符截断 | 形式接近，缺「索引 + 主题文件」分层，截断不透明 |
| 按需层 | 主题文件/检索/JIT | `.agent-context` 软提示 + 模型 read | 有雏形，但没有触发规则与预算 |
| 检索 | 多信号/结构化 | 中文 bigram 关键词，按文件 | 明显落后；模型选择器未接线 |
| 写入 | 抽取 + 更新/删除 | 抽取（绕过准入）+ 人工审批 + 追加 | 治理更严，但更新/删除缺失，抽取链路失控 |
| 生命周期 | 失效/有效期/TTL | lastVerified + 90 天标注 | 只有标注，没有动作 |
| 溯源 | episode/来源链接 | 事件里有 proposalId，落盘条目没有 | 落盘即断链 |
| 作用域 | 写入前分区 | workspace 硬边界；scope 只写不读 | 基本可用，`user` scope 名不副实 |
| 可观测 | 管理页/上下文查看 | MemoryTab + 事件标签；无健康度/实际注入量 | 事件全，消费端弱 |
| 成本 | 后台抽取有预算 | 默认每轮抽取、门槛 3 字、未计量 | 成本不可见，可能偏高 |

## 5. 漏洞与缺陷清单

> 分级：**P0** 数据丢失/验收口径被破坏/审计失真；**P1** 治理与语义错误；**P2** 效率、可维护性与测试缺口。
> 每条给「证据 → 后果 → 建议方向」。建议方向只描述目标，不是实施授权。

### 5.0 先说「计划债」：两套承诺 vs 现状

这轮审计最刺眼的不是「没人想到」，而是**问题早被写下、验收标准也写了，但大多没落地**。

**（A）`docs/plans/2026-09-17-001` 阶段 5「记忆准入与生命周期治理」**（`docs/plans/2026-09-17-001-重构-事件流执行脑图记忆治理与工作区隔离计划.md:380-432`）

| 计划要求 | 现状 | 判定 |
|---|---|---|
| 结构化字段 `scopeType/kind/canonicalKey/sourceRefs/stability/expiresAt/status/supersedes/sensitivity` | 只加了 `scope/confidence/lastVerified`（`记忆元数据.mjs:15-21`） | 大部分未做 |
| 服务端硬拒绝九类内容（敏感/临时/无来源数字/任务摘要/Harness/无关联/语义重复冲突/多事实/单次偏好） | 只对 `memory_update` 生效；抽取绕过；「无来源数字/多事实/单次偏好」无规则 | 部分 |
| `memoryPolicy` 真正生效（manual 同时禁工具与沉淀提示） | 只禁工具，抽取仍写 | 未完成 |
| 每 Run 默认最多一条候选 | 仅靠「本轮已直接写则跳过抽取」间接限制；多次 `memory_update` 不受限 | 未做 |
| pending 14 天过期、临时经验 1–7 天、工具经验 30 天 | 无 TTL | 未做 |
| approved 支持 revoke/supersede | 无 | 未做 |
| rejected 保留 30 天后归档 | 永久保留 | 未做 |
| 禁止全局无差别 `slice(-300)` | 仍是 `slice(-300)`（`记忆管理.mjs:77`） | 未做 |
| 按 workspace/project 分区 + 写入加锁 | 全局单文件、无锁 | 未做 |
| `MEMORY.md` 降级为投影，JSON 为事实库 | `MEMORY.md` 仍是唯一事实库 | 未做 |
| 检索注入按 规则→偏好→Top-K 事实→索引→经验，停止固定 1500 截取 | 仍是固定 `slice(0,1500)`（`agent.mjs:8243`） | 未做 |
| 注入块带 memory ID/版本，撤销后处理会话残留 | 无 ID/版本 | 未做 |
| 面板与 Agent 实际读取范围一致（`.txt`/子目录） | 面板可见但 Agent 不读（`index.mjs:6284-6296` vs `记忆召回.mjs:68`） | 未做 |
| 面板编辑记录来源/时间 | 只有 `memory_file_edited` 事件，文件内无来源 | 部分 |

该计划是 2026-09-17 写的，至今两个多月；仓库里没有对应的 ADR 宣布放弃或降级。**结论：当前记忆系统的多数缺陷属于「计划债」，不是未知风险。**

**（B）`docs/决策记录/0043`「新功能运行开关全部默认打开」**（2026-11-19）

- 该 ADR 的后续条款写明：新增开关是否默认开，按「已过全量回归 + **有守护测试**」判断（`0043-新功能运行开关全部默认打开.md:31`）。
- 记忆抽取/召回随后默认打开（`运行开关.mjs:340,344`），但抽取链路的守护测试是**字符串断言**（`记忆准入治理测试.mjs:79-83`），没有覆盖准入绕过与 `manual` 策略；也没有「注入记账」测试。
- **结论：`memoryExtract` 的默认开启不满足 ADR 0043 自设的门槛。** 这不是反对默认开，而是默认开之前该补的行为测试没补。

### P0

**M-01 自动抽取绕过准入与项目策略（R14 实质违规）**
- 证据：`server/执行句柄.mjs:374-389` 解析后直接 `createMemoryProposal`；对比 `agent.mjs:5374-5396` 的 `manual` 检查与 `evaluateMemoryCandidate`。
- 后果：敏感信息、临时环境、Harness 内部实现、重复内容可进入候选池并在面板展示；`manual` 项目仍被自动沉淀。R14「敏感信息不进入记忆」「不会静默写入」被绕过（虽然仍需批准才落盘，但候选库已经持有内容）。
- 建议：抽取链路复用同一个 `evaluateMemoryCandidate` 与 `memoryPolicy`；`manual` 直接跳过抽取。

**M-02 测试污染真实候选库 + 300 条 FIFO 静默淘汰（可复现数据丢失）**
- 证据：`scripts/记忆元数据测试.mjs:118-150` 未设置 `OAW_MEMORY_PROPOSALS_FILE`；`记忆管理.mjs:14,76-78` 整文件 `slice(-300)`。
- 现场：8 条 `%TEMP%\oaw-mem-*` 记录（7 条 approved），最新一条由本次 `test:memory-metadata` 产生；真实 approved 仅 3 条。
- 后果：每次 `verify` 追加候选；超过 300 条后最早的 pending 被无声删除（无事件、无备份）。测试工作区删除后这些候选永久指向不存在的路径。
- 建议：测试统一指向临时 proposals 文件；淘汰改为「归档 + 事件 + 只淘汰终态」，pending 不淘汰。

**M-03 召回预算与注入记账失真，且段预算比 1500 更早截断**
- 证据：`agent.mjs:8190-8196` 以 60KB 组装；`8243` 切 1500 字符；`上下文段落.mjs:33,44-52` 再把整个 dynamic-context 段按 6000 字节从头截断；`记忆召回.mjs:236` 的 `injectedBytes` 是组装量，`truncated` 只看单文件（`223`）。
- 实测：当前 Work 动态上下文 5669 字节（固定前缀 3783 + 记忆块 1886），只剩 331 字节；合成 1150 字符记忆时动态上下文 6474 字节，截到 5999 字节后尾部的「经验教训」标记消失。
- 后果：事件/对象栏显示「注入 N KB、未截断」，模型实际只看到前缀；今天 750 字符/1810 字节刚好没被切，但再增加约 2–3 条记忆就开始丢尾部。排查「为什么代理没记住」时会被事件误导。
- 建议：区分 `assembledBytes` / `renderedBytes` / `injectedChars` / `droppedChars`；段预算截断必须同时置 `truncated` 并给出丢弃量；记忆应放在固定前缀之前或拥有独立预算。

**M-04 读取路径的四重静默截断，最后一重只剩 331 字节**
- 证据：`上下文段落.mjs:33,44-52`（dynamic 段 6000 字节）→ `agent.mjs:8243`（1500 字符）→ `agent.mjs:1135`（分层总 2800 字符）→ `agent.mjs:1080-1087`（每文件 1800 字符）；`MEMORY.md` 是单文件 append-only。
- 实测：固定前缀 3783 字节 + 当前记忆块 1886 字节 = 5669/6000，余 331 字节（约 110 个汉字）；13 条记忆共 491 字符，约占 1500 字符闸的 1/3，但在段预算上已经只剩 2–3 条的余量。
- 后果：记忆增长时先丢「经验教训」等末段分类；今天就已接近段预算上限，而所有事件都显示正常。召回路径看似读全文（60KB），最终仍要过段预算与 1500 两道闸。
- 建议：记忆独立预算并优先于固定前缀；`MEMORY.md` 拆「索引 + 分类/主题文件」；截断按条目记账并显式告知模型与用户。

### P1

**M-05 审批即「今天核验」，虚假新鲜度**
- 证据：`记忆元数据.mjs:52` 默认 `lastVerified=今天`；`记忆管理.mjs:254` 批准时未传 `lastVerified`。
- 后果：几天前抽取、从未复核的内容，批准当天就被标成「今天核验过」，90 天 stale 机制被推迟；「核验」语义被稀释为「点击批准的时间」。
- 建议：区分 `extractedAt` / `approvedAt` / `lastVerified`；只有用户显式「已核对」才更新 `lastVerified`。

**M-06 落盘丢失溯源**
- 证据：`记忆管理.mjs:254,266-268` 只写 content + 元数据；`proposalId/runId/threadId` 只在 `memory_written` 事件里。
- 后果：无法从 `MEMORY.md` 的一行反查「哪次运行、哪条证据、谁批准的」；审计只能靠内容文本 join 事件。
- 建议：条目行尾加稳定的 `id`（或独立 `memory/index.json` 映射），保留 proposalId/runId。

**M-07 `scope` 只写不读**
- 证据：`记忆元数据.mjs:15` 定义 `workspace/project/user`；`记忆管理.mjs:170-173` 写入；召回/分层无任何 scope 过滤（全仓库搜索仅元数据模块与测试使用）。
- 后果：`scope=user` 的偏好仍只存在当前工作区，换项目即丢失；UI/工具语义误导。
- 建议：要么把 scope 用于读取路由与展示，要么从工具参数中移除，避免假能力。

**M-08 无生命周期动作**
- 证据：无 supersede/revoke/TTL/删除 API；stale 只加文本标注（`记忆元数据.mjs:117-134`）；`rejected/merged` 没有主动归档，只会一直留到被 300 条 FIFO 淘汰。
- 后果：104 pending、44 条超 30 天；错误/过时记忆只能靠用户手工编辑 `MEMORY.md` 删除，且删除后无审计；stale 只影响提示文案，不会生成待复核任务。
- 建议：补 `supersede/revoke` 状态与最小 TTL；stale 进入「待复核」队列而不是只加一行字。

**M-09 候选库无锁的读-改-写**
- 证据：`记忆管理.mjs` 的 create/edit/reject/merge/approve 均 `readStoredProposals → 改 → saveStoredProposals` 整文件覆盖；无 `acquireWriteLock`。
- 后果：两个标签页审批、或自动抽取与 UI 审批并发时丢更新；300 条上限下还可能把刚写入的候选覆盖掉。
- 建议：候选库级锁或按 workspace 分片 + 原子 CAS；至少对写操作串行化。

**M-10 记忆与工作区规则的权威位置倒置、组成漂移**

**M-11 候选按工作区过滤 + 全局存储 → 大量候选永久不可见**

**M-12 文件面板与候选列表的工作区分叉（2026-10-11 已记录，仍未修）**

**M-13 批准不是事务：写冲突 500、异常可能「部分生效」**

**M-14 抽取触发门槛过低，成本归不到父 Run，且没有轮次/超时预算**

**M-15 重复判定、分节与合并的作用域过窄**

**M-26（P1）用户输入在 20000 字节处静默截断（顺带发现）**

**M-28（P1）静态工具规则每轮重复注入**

| W15 面板编辑绕过 | CONFIRMED | 直接 `atomicWriteFile`，无元数据/准入/审批事件 |
| W16 长度口径 | CONFIRMED | 行号应为 `agent.mjs:5349-5350,5360`；100/220/1200 三处 |

**复核者新增、原清单未覆盖的问题**：敏感拒绝事件回显原文（NF1→M-21）、审批/编辑/合并绕过准入（NF2→M-22）、候选库损坏清零（NF3→M-23）、审批非事务（NF4→并入 M-13）、去重/分节/合并过窄（NF5→并入 M-15）、段预算先截断（N1→M-03/M-04）、用户输入 20k 字节截断（N2→M-26）、AGENTS.md reload 不重建 system prompt（N3→M-24）、threadId 路径穿越 + 快照堆积（N4→M-25）、可见面/读取面不一致与召回 query 污染（N5→§3.3/M-27）。

### 6.3 被推翻或修正的结论

1. **「1500 字符是主要注入上限」→ 错。** 主约束是 dynamic-context 段的 6000 字节；固定前缀 3783 字节，记忆只剩约 2.2KB，今天就只剩 331 字节余量。
2. **「事件今天已经高估注入量」→ 不准确。** 今天召回文本 750 字符/1810 字节，尚未触 1500；高估在超过实际截断后才发生，段预算截断时反而可能仍报 `truncated=false`。
3. **「子代理完全拿不到记忆/规则」→ 过强。** 默认不注入，但有 `read` 工具可主动读取。
4. **「召回命中后规则层完全消失」→ 过强。** 当前 MEMORY.md 被选中时规则仍在召回正文；只有未入选或超 8KB 才丢。
5. **「抽取成本未计量」→ 错。** 会计入用量库，但 `runId=null / actorKind=main`，无法按父 Run 归集（实测 42/577）。
6. **「rejected/merged 永久堆积」→ 不准确。** 它们同样会被 300 条 FIFO 淘汰；问题不是「永久」而是「无声」。
7. **行号与数量修正**：manual 断言 `:84-92`；W16 `agent.mjs:5349-5350,5360`；候选库 114/104/10；temp 记录 8 条；快照 56 个/134KB（不是 224KB）。
8. **新增的严重问题**：拒绝事件回显敏感原文（M-21）、审批链绕过准入（M-22）、候选库损坏清零（M-23）、AGENTS.md 热更新失效（M-24）、threadId 路径穿越（M-25）。

### 6.4 Steelman：现状可能是合理取舍的地方

- **单用户本地应用**：审批链的人为摩擦是有意设计，防止模型污染长期记忆；不能用 SaaS 的自动化程度要求它。
- **不引入向量库**：符合 AGENTS.md「不引入数据库/微服务」的约束；关键词召回是可解释、可审计的务实选择。
- **1500 字符上限**：可能是首字延迟与上下文体量的主动取舍；问题不在上限本身，而在**记账与截断不透明**。
- **`lastVerified=批准日`**：可以解释为「用户此刻背书」，但应把「内容核验」与「审批动作」分开，否则 stale 语义失真。
- **测试写真实候选库**：可能是早期为了省事；在单机开发环境里危害有限，但与 300 条 FIFO 组合后变成数据丢失路径，不能继续保留。

### 6.5 残余不确定性

1. Pi 的 compaction 对历史中重复记忆块的处理未实测；理论上每轮重注入可弥补，但旧副本可能进入摘要。
2. `AGENTS.md` 热更新：已确认「普通连续对话不会重建 system prompt」；但 Pi 是否在工具集变化、会话恢复等其他路径重建，未穷举。
3. `selectMemoriesWithModel` 是否有外部调用方（插件/脚本）未穷举；当前仓库内无生产调用。
4. 候选库并发丢更新的实际概率未压测；代码层面无锁是确定的。
5. Windows 路径正则 `OTHER_WORKSPACE` 只覆盖 `X:\`；POSIX 路径未覆盖（当前产品以 Windows 为主）。
6. threadId 路径穿越需要能访问本机 API（默认无 token）；浏览器跨源被「无 CORS」挡住，本地进程不受限，实际威胁模型是「本机恶意/误用」。

## 7. 建议路线（未授权实施，仅供决策）

### 批次 0：止血（P0，不改变产品语义）

1. **记忆预算与记账**：给记忆独立预算或把记忆放在固定前缀之前；事件拆 `assembledBytes` / `renderedBytes` / `injectedChars` / `droppedChars`；段预算或 1500 切片任一触发都必须置 `truncated`（M-03/M-04）。
2. **抽取链路接治理**：`执行句柄.记忆抽取` 复用 `evaluateMemoryCandidate` 并读取 `memoryPolicy`；失败/取消不抽取（M-01/M-14）。
3. **拒绝事件脱敏**：`memory_proposal_rejected` 不再携带原文，最多给长度/分类/哈希；排查历史 `.oaw/runs` 是否已有密钥（M-21）。
4. **审批链统一准入**：编辑、合并、批准前都跑同一套规则（至少敏感信息与 220 字），或在 UI/文档明确「人工编辑视为直接授权但敏感信息仍拦截」（M-22）。
5. **候选库数据安全四件套**：测试固定 `OAW_MEMORY_PROPOSALS_FILE` 到临时文件；写操作加锁/串行化；损坏 JSON 拒绝写入并备份而不是返回 `[]`；淘汰只针对终态并归档 + 事件（M-02/M-09/M-23）。
6. **审批事务化**：带重试写锁 + 捕获冲突；编辑/写记忆/改状态可回滚；失败标 `failed` 而非 500 后留 pending（M-13）。
7. **threadId 白名单**：拒绝 `/`、`\`、`..`；快照清理或保护（M-25）。

### 批次 1：读写闭环（P1）

8. **`MEMORY.md` 拆分**：索引（一行一条）+ 分类/主题文件；读取按条目记账；frontmatter 支持一层嵌套或统一行尾元数据；描述取首条内容而非 H1（M-16/M-17/M-04）。
9. **记忆移出用户消息**：作为独立「背景/记忆」段并标注权威等级；工作规则只来自 `AGENTS.md`（M-10）。
10. **`scope` 要么参与读取路由/展示，要么从工具参数移除**（M-07）。
11. **元数据与溯源**：拆分 `extractedAt/approvedAt/lastVerified`；条目带稳定 id 与 `proposalId`（M-05/M-06）。
12. **最小生命周期**：`revoke/supersede`、pending 过期、stale 进入待复核队列（M-08）。
13. **AGENTS.md 热更新**：reload 后重建 system prompt，或明示「新会话生效」（M-24）。
14. **用户输入截断提示**：长输入被截断时明确告知模型与用户（M-26）。

### 批次 2：演进（P2）

15. **检索升级**：先做「索引 + 条目级关键词 + scope 过滤 + 原始用户文本做 query」；向量检索单独立 ADR（受「不引入数据库」约束）。
16. **UI**：全部工作区候选视图与计数徽标、记忆健康度、本轮实际注入预览（「这次用了哪几条」）。
17. **子代理规则卡**：按角色注入 ≤500 字精简规则，或显式要求先读 `AGENTS.md`。
18. **可见面/读取面一致**：递归读取或面板标注「不参与模型读取」（M-27）。

### 明确不做（本轮建议）

- 不引入向量数据库/图数据库/微服务（需 ADR）。
- 不做 Agent 自编辑记忆（保留人工审批）。
- 不放开 `manual` 项目的自动沉淀。
- 不把 `AGENTS.md` 纳入自动抽取范围。

## 8. 可测的验收口径

1. 跑完 `test:memory-*` 与 `verify` 后，真实 `.oaw/memory-proposals.json` 条目数不变（隔离）。
2. 候选超过上限时，pending 数量不减少；被淘汰的只有终态，且有归档与事件。
3. 抽取链路：含 `sk-`/密码/临时环境的输入不产生候选；`memoryPolicy=manual` 的项目不产生候选（行为测试，不是字符串断言）。
4. 每轮 `memory_recall_selected` 的 `injectedChars` 等于动态上下文里实际出现的记忆字符数；发生最终截断时 `truncated=true`。
5. 构造 20 条、超过 1500 字的 `MEMORY.md`，断言「经验教训」分类仍可被召回或在截断报告中明确列出。
6. 并发两个批准请求，候选状态与 `MEMORY.md` 条数一致（无丢更新、无重复）。
7. 批准后 `MEMORY.md` 条目可反查 proposalId/runId。
8. `metadata.type` 嵌套 frontmatter 的文件在 manifest 中类型正确；`MEMORY.md` 描述不是 H1。
9. 子代理能读到一份精简规则（或有明确「不继承」的说明与替代方案）。
10. 不同工作区切换时，`/api/memory` 文件列表与候选列表的 workspace 一致。
11. `memory_proposal_rejected` 事件的 payload 不含原文（只含 code/长度/哈希）。
12. 面板编辑或合并候选后点批准，敏感信息与 220 字上限仍然生效。
13. 手工写坏 `.oaw/memory-proposals.json` 后，下一次写入不覆盖原文件，且给出可恢复错误。
14. 修改工作区 `AGENTS.md` 后，下一轮或明确的下一个会话生效；有测试证明 system prompt 已重建。
15. `threadId` 含 `..`、`/`、`\` 时被拒绝，或文件名被安全转义，不产生工作区外写入。
16. 长用户输入被截断时，模型回复或 UI 中有明确提示。
