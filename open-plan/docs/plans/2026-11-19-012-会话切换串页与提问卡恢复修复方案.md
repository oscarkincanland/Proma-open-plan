> 级别：S3（跨 client / server 两模块，含运行时数据清理一项）　日期：2026-11-19　状态：✅ 已确认（2026-11-20 用户批准）并已实施，见[实施记录](2026-11-19-012-实施记录.md)

## 0. 背景与根因（附实证）

### 缺陷一：切会话串页（运行中气泡泄漏进另一会话）

- **复现**（2026-11-19 端到端探针，会话 A=运行中的 echart 任务、会话 B=已完成的"帮我来写篇文字材料"，同一 client-2jc5ynvu / 日常任务吧工作区）：A→B 切换后 B 视图消息数 2→3，多出的第 3 条是 **A 的流式气泡**（首拍 `23:32 正在分析请求`，A 快切轮次出现 A 正文「行业下行，能」）；该文本在 A/B 两会话 JSONL 与 Run 文件中均不存在（尚未落盘的流式内容），证明是 A 的实时态泄漏，而非 B 自身历史。
- **根因**：`client/src/components/ChatPanel.jsx` 历史水合的「保留流式气泡」合并逻辑（L1722–L1750）。切换会话的那次提交里，水合 effect（L1692）**先于**线程切换 effect（L1906）执行，此时 `messagesRef.current`（L751-752，经 useEffect 赋值＝上一次提交值）仍持有上一会话 A 的消息；L1722 `find(item => item.role === "assistant" && item.status === "streaming")` **没有校验气泡属于哪个会话**，直接把 A 的运行中气泡并入 B 的历史列表。泄漏气泡此后随每次 A↔B 往返被重新合并（仍在 messagesRef 里且 status 仍为 streaming），不会自愈。
- **为什么久修不好**：此前修复覆盖了「切回运行中会话冻结」（streamAttachAllowed = agentReady || busy）、「回放事件围栏」（finishedRunIdsRef / activeRunIdRef，L2903-2916）、「切线程清提问去重集合」（L1915），但这条**数组直接合并**路径不经过事件围栏，三条防线全部绕过。

### 缺陷二：asku（提问卡）在切换/刷新后消失

- **实证**（2026-11-19 对本机 3002 服务实测）：`GET /api/interactions?client=client-f98rrzln&thread=…`（裸键，浏览器实际发出的形态）返回 **0 条**；同一记录改用全键 `client=client-f98rrzln::thread-0b99dd62…` 查询返回 **1 条**。`.oaw/interactions.json` 中存在一条 status=open 的待答交互可供对照。
- **根因**：交互记录的 `clientId` 字段存的是 agentKey 全键 `client-xxx::thread-yyy`（写入点 `server/agent.mjs:5428-5443`，createInteraction 入参 clientId=agentKey），而浏览器恢复查询只传裸键（`client/src/components/ChatPanel.jsx:1214`，`getClientId()` 产 `client-xxxxxxxx`，见 `client/src/api.js:413-420`）；服务端过滤用全等比较（`server/交互中枢.mjs:85`）→ **恢复接口对真实浏览器客户端恒返回空**。
- **症状链**（人机协作枢纽 interactionHub 默认开启，`server/运行开关.mjs:163`）：`ask_user` 实时事件只带最小载荷，客户端先合并事件再调 `refreshInteractions()` 补全载荷（ChatPanel.jsx:3397-3400，事件注释明言「补一次 GET 拿到 question/options/fields」）→ GET 恒空 → `setInteractions([])` **把刚合并的提问卡冲掉**。切会话（L1224-1231 清空并重拉）、刷新、SSE 重连（L3021）都会触发同一冲刷 → 待答提问在界面上不可见、不可答。
- **次生问题**：`交互中枢.mjs:86` 的 `!item.threadId ||` 分支让 threadId 为空的记录匹配**所有**会话；实测存在一条 2026-09-28 遗留的 open 记录（threadId=""、expiresAt=null，`itx_0de4dfd1-228e-4b8f-8035-0bfb39a61632`），客户端过滤修好后它将只在「key 内嵌线程」显示，但仍是永不过期的僵尸卡。

## 2. 缺陷一修复：气泡 thread 归属标记 + 水合合并过滤

**契约**：实时创建的流式气泡必须携带创建时的 `threadId`；水合合并只保留「属于当前会话」的流式气泡。不改事件、不改存储。

1. **创建点打标**（4 处，均为 `status: "streaming"` 的消息字面量，追加 `threadId: threadId` 字段；全 client/src grep 证实创建点仅此 4 处，另有 L3589/L3602 两处 patch 复用不改归属）：
   - L2963 `ensureAssistant`（事件驱动恢复气泡，泄漏源）
   - L3598 模型重试气泡
   - L4533 发送消息气泡
   - L1887 提问卡恢复气泡（同病同治，防同类泄漏）
2. **合并过滤**（L1722 一处）：`liveStreaming` 查找条件追加 `String(item.threadId || "") === String(threadId || "")`。无标记的旧气泡视为「非当前会话」丢弃（安全默认：全部实时气泡经上述 4 点创建后必带标记；历史消息恢复后 status 均为 "done"，App.jsx:285，不受影响）。
3. **自愈**：已污染页面的旧气泡在下次水合时因标记不匹配被丢弃，无需迁移。注意：泄漏气泡若已随切换存入目标会话 threadCache（L1921），缓存命中路径（L1941）不经合并，水合到达前可能**闪现一次**——水合完成后即清除，验收判定须在水合完成后读取（§7 P1）。

**边界核对**（已逐条过）：
- 切回运行中的 A：缓存恢复带标记气泡（标记=A）→ 合并保留 → 实时续写不受影响；effect 内 handler 经 ref 每次渲染转发最新闭包（L4076-4077），打标取值新鲜，可行；
- 「加载更早」appendOnly 路径（L1700-1705）不走该合并，不受影响；
- 主链路 threadId 恒为非空 `thread-<uuid>`（App.jsx:644-650、1215），`threadId=""` 分支在当前代码中不可达；`String(item.threadId || "") === String(threadId || "")` 比较作为防御保留（对抗审查 M3 修订：原表述「新建未保存会话 threadId 为空」与代码不符，已纠正）；
- 线程切换 effect 内 `if (!hydratingHistory)` 的缓存恢复路径（L1941）恢复的是按线程缓存的消息，天然带正确标记，不改；
- 消息对象新增 `threadId` 字段与既有字段无冲突：全 client/src grep 证实消息字面量均无 threadId；ChatPanel.jsx:7783 的 `previous.threadId === next.threadId` 是组件 props 比较（当前线程 prop），与消息对象字段不同层级。

## 3. 缺陷二修复：交互恢复接口匹配兼容（读侧）

`server/交互中枢.mjs:82-93` `listActiveInteractions` 过滤改写，**保留既有空参短路前缀不变**（`!clientId ||`、`!threadId ||`——metrics 无参调用 index.mjs:5211 与内部查询依赖它们放行，对抗审查 M4 修订），仅替换其后的比较逻辑：

1. **客户端匹配**：`item.clientId === clientId || clientPart(item.clientId) === clientPart(clientId)`，其中 `clientPart = (v) => String(v || "").split("::")[0] || ""`（记录与查询参数均兼容全键/裸键；裸键由 `getClientId()` 生成 `client-` + base36，不含 `::`，无歧义）。
2. **线程匹配**：保留 `!threadId ||` 短路；比较改为按「生效线程」——`item.threadId`（非空优先）→ 否则取 `item.clientId` 内嵌线程段（`split("::")[1] || ""`）→ 仍为空视为「真无线程记录」，维持现状放行（拍板点 2）。修复后僵尸记录只能在其 key 内嵌线程（thread-0b99dd62…）显示，不再跨会话。
3. **不动**：`createInteraction` 写入侧不改（新记录继续存全键，读侧已兼容，避免双写口径）；审批投影（index.mjs:5178-5205）不改（同病披露与理由见 §6）；metrics（无参调用）行为不变（空参短路保留）。

## 8. 测试计划（对抗审查 H1 修订：行为级回归为主，结构断言为辅并标注）

**缺陷一主守护 = 可复跑行为级回归（新增脚本）**：《开发收敛规范》§3 明文不接受「只读源码正则」作为主要守护——这正是该缺陷三轮修复拦不住的结构性原因。新增 `scripts/会话切换串页回归测试.mjs`：Playwright 加载真实 client bundle（依赖 npm start，同 ui-smoke 前置），`page.route` stub 数据面（/api/sessions、/api/sessions/:id、/api/runs、/api/agent/stream 的 SSE 响应体），不依赖真实模型与真实会话数据：
- 会话 A：历史含 run 摘要（status=running）+ SSE 回放注入 token 事件 → A 视图出现 streaming 气泡；
- 会话 B：仅历史消息，无运行；
- 判定：A→B→A→B 两轮往返，**每次切到 B 后（水合完成标志：B 的历史消息已渲染）**，B 视图 `.msg` 数与指纹同 B 基线、无 `.msg.streaming` 元素；切回 A 后 streaming 气泡仍在（不误删合法气泡）。
- 局限声明：stub 的是数据面，SSE 帧为整段回放体；覆盖合并泄漏路径，不覆盖真实时序下的所有竞态。

**辅助守护 = 结构断言（标注豁免）**：`scripts/会话切换稳定性测试.mjs` 增断言（4 创建点含 `threadId: threadId` 字面量、合并处含归属比较）。按《开发收敛规范》§3 标注为**结构断言**：只防实现被回改，不验证打标运行时取值正确性（后者由上述行为回归与一次性人工 E2E 留痕 docs/audits 兜底）。

**缺陷二守护**（`scripts/交互中枢测试.mjs` 函数级用例，真行为断言非假测试）：①全键记录 + 裸键查询可见；②全键记录 + 全键查询可见；③`clientId="c::thread-1"`、`threadId=""` 记录按 thread-1 可见、按 thread-2 不可见；④**同 client 两条全键记录（thread-1/thread-2）互斥**：查 thread-1 时 thread-2 记录不可见（跨会话可见性本质用例，对抗审查 L5 补充）；⑤真无线程记录（`clientId="c9"`、无 `::`）带 thread 查询仍可见（现状兼容）；⑥metrics 无参调用不受影响（空参短路）。

## 9. 风险与回滚

- **风险 1**：effect 顺序耦合（水合先于线程 effect）是根因前提——本方案采用「数据归属」判定，不依赖顺序，天然抗重排。
- **风险 2**：`clientPart` 宽松匹配理论上允许同前缀不同 thread 的客户端互相看到记录——客户端 id 为随机 10 位 base36，碰撞概率可忽略；且线程过滤独立生效。
- **风险 3**：标记遗漏的隐藏创建点导致合法气泡被误删——已全仓 grep `status: "streaming"`（4 处创建 + 2 处 patch 复用，对抗审查 L1 修正：patch 为 2 处非 3 处）；行为回归覆盖「切回运行中会话续写」场景兜底验证。
- **风险 4**：新回归脚本 stub SSE 的方式若与服务端帧格式漂移会假失败——脚本内断言失败时输出实际收到的帧样本，便于区分环境漂移与真回归。
- **回滚**：见 §4。
