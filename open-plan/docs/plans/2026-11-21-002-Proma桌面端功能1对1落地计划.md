## 1. 目标

把 open-plan（规聚）当前全部产品能力（PRD R1–R17）在 Proma fork 的桌面端形态上 1:1 可用，得到一个可安装、可分发的「规聚桌面版」：

- 界面与交互 = open-plan 现有 React SPA（视觉不重做）；
- 服务端 = open-plan Express 单服务（业务零重写）；
- 桌面外壳 = Proma Electron（窗口、托盘、菜单、单实例、原生对话框）；
- Proma 桌面特性（灵动岛、子会话面板、内嵌终端等）作为后期增强逐项打通，不做首期承诺。

## 2. 两边现状（事实基线）

### 2.1 Proma fork（壳基座）

- Bun workspace monorepo：`packages/{core, session-core, shared, ui}` + `apps/{electron, cli}`，全 TypeScript。
- Electron **43.2.0** + electron-builder 25，asar + asarUnpack 管理原生模块（node-pty、esbuild、pi-tui native 等）。
  注意：Electron 43 内置 Node 的具体版本**本地未验证**；硬口径是 Pi SDK 的 `engines.node >= 22.19.0`，P0 必须实测 `process.versions.node` 达标（见 P0 任务 3）。
- 主窗口加载：dev `loadURL('http://127.0.0.1:5173')`，prod `loadFile(renderer/index.html)`（[apps/electron/src/main/index.ts](file:///C:/Users/jijec/.cache/reference/proma-open-plan/apps/electron/src/main/index.ts)）——**存在加载本地 HTTP 服务的现成先例**。
- preload 经 `contextBridge` 暴露 `window.electronAPI`（约 3100 行白名单桥）。
- Agent 内核：`agent-orchestrator.ts` 经 EventBus 解耦，调用 `@proma/core getAdapter`（Pi 0.87.1），与 renderer 无硬耦合——可旁路。
- 已有「Pi runtime 作为主进程 external 运行 + `sync:runtime-deps` 依赖闭包同步到 node_modules」的打包先例，外部 Node 服务随包有路径可循。

### 2.2 open-plan（应用内核）

- `server/index.mjs`：Express 5 单服务，`HOST/PORT` 可配，`OAW_API_TOKEN` 全局 token 鉴权（timingSafeEqual）。**注意**：server 注册了全局 `process.on("uncaughtException") → process.exit(1)`（依赖启动脚本的监督循环拉起），并有全局 unhandledRejection 处理——**不适合进程内 import 进 Electron main**（见 D2）。
- `server/服务入口.mjs`：**已有完整桌面嵌入链路**——`pickFreePort()` 随机端口 → 生成启动期 token（全程有效）→ 注入 `OAW_DESKTOP/OAW_API_TOKEN/HOST/PORT` → 动态 import `server/index.mjs` → 轮询 `/api/status` 就绪（[server/服务入口.mjs](file:///d:/Claude%20code%E6%96%87%E4%BB%B6/office-agent-web/server/服务入口.mjs)）。仅依赖 Node 内置模块，纯 Node 可跑、无 Electron 依赖。
- 直接依赖无原生编译模块（Pi 系依赖均为 JS/WASM），原生 ABI 风险低。
- `desktop/src/main.cjs`：`resolveClientDist()` + `loadRenderer()`（`service.url/?token=`）。
- 平台适配层（ADR 0024）：业务代码「问能力不问形态」，原生对话框/外部打开等已有抽象（`client/src/平台/`）。
- 运行数据：工作区 `office-workspace/` + `.oaw/`，desktop 模式 roots 已动态化（v0.11.56）。
- 功能全景：PRD R1–R17（文档办公、Agent 协作、对话流、引用、会话、智能体/技能、批注、主题、知识库、地图 GIS、模板、工作区、任务中心、记忆、供应商、系统集成、创作画布）。

### 2.3 关键结论

open-plan 现有 desktop 壳的模式（main 进程 import server + 随机端口 + token 加载 SPA）与 Proma 的窗口机制**同构**。嵌入的本质工作是：**把 open-plan 应用树迁入 Proma 仓库 + 把「启动服务 → loadURL」接进 Proma main 进程 + 平台桥适配**，R1–R17 业务代码基本零改动。

## 3. 总体架构

```
GuiJu/Proma 桌面应用（Electron 43.2.0, main 进程）
├─ 启动编排：spawn sidecar（ELECTRON_RUN_AS_NODE）→ pickFreePort + token → 探测就绪 → restart-on-exit 监管
├─ open-plan server（Express 5 + Pi 1.5.1，独立子进程，原生 ESM，随包 extraResources）
│   ├─ 业务全景 R1–R17（迁移不重写）
│   └─ 数据根：用户数据目录（工作区/`.oaw`/maps，desktop roots 动态化）
├─ BrowserWindow（主窗口）→ loadURL(http://127.0.0.1:<port>/?token=...)
│   └─ open-plan React SPA（R1–R17 界面，迁移不重写）
├─ Proma 桌面件：托盘 / 菜单 / 单实例锁 / 原生对话框（经 preload 桥供 SPA 调用）
└─ Proma Agent 件（灵动岛 / 子会话面板 / 内核 0.87.1）：首期旁路，后期经事件桥接入
```

**进程模型（sidecar 隔离）**：open-plan server 以**独立子进程**运行——Proma main 用 `ELECTRON_RUN_AS_NODE=1` spawn Electron 自身执行 `open-plan/server/服务入口.mjs`（或等价 sidecar 入口），main 经 `service.url + token` 探测就绪后加载窗口。理由：
1. server 的 `uncaughtException → process.exit(1)` 语义与「监督循环拉起」假设，在进程内 import 下会**杀死整个 Electron 壳**且 fork 仓库无监督循环——sidecar 天然隔离，main 进程只做 restart-on-exit；
2. Proma main 是 esbuild 打包的 CJS 产物，open-plan server 含 `import.meta`（goal.mjs、kb.mjs 等 6 处），进程内 import 需要额外的 external 处理——sidecar 让 server 保持原生 ESM 零改打包；
3. ADR 0024 已记录「主进程承载后端、重任务移出主线程」的负面后果，sidecar 直接消除该风险。

**双内核策略**：Proma 的 agent-orchestrator（Pi 0.87.1）首期**不启动、不删除**（旁路保留）；业务会话全部由 open-plan server 内嵌的 Pi 1.5.1 运行时承担。两套 SDK 依赖通过目录隔离（open-plan 自带 node_modules 闭包）避免版本冲突。

## 4. 关键技术决策

| # | 决策 | 内容 | 理由 |
|---|---|---|---|
| D1 | 仓库组织 | **单仓并入**：Proma fork 新增顶层 `open-plan/` 目录，承载现有 client/ + server/ + 配置（整树迁入，保留文件命名现状）；开发主线转移到 fork 仓库 | AGPL 衍生需整体开源，单仓最简；避免双仓同步负担 |
| D2 | 启动方式 | **sidecar 子进程为默认**：Proma main 用 `ELECTRON_RUN_AS_NODE=1` spawn Electron 自身执行 `open-plan/server/服务入口.mjs`，main 做就绪探测 + restart-on-exit；不做进程内 import（server 的 `uncaughtException→exit` 语义与 CJS 打包 + `import.meta` 冲突使其不可行） | 崩溃隔离干净；server 保持原生 ESM 零打包改造；消除 ADR 0024 记录的主进程承载后端负面后果 |
| D3 | 平台桥 | open-plan `client/src/平台/` 新增「Proma/Electron 桥」适配器：检测 `window.electronAPI`，将原生文件对话框、外部打开、定位映射到 Proma preload 既有 API（`openFileDialog` / `openFileOrFolderDialog` / `openFile` / `showItemInFolder`，白名单已存在，只复用不新增 IPC 面） | 平台层「问能力不问形态」已抽象；Proma preload 既有桥接面直接够用 |
| D4 | 数据根与 token | 桌面版数据根 = `app.getPath('userData')/guiju-data/`（工作区、`.oaw/`、maps、designs），经既有 oaw-data roots 动态化机制注入，首次启动引导选择工作区。token 口径**继承现状**：启动期生成、全程有效，经 `/?token=` 进 UI；外泄缓解依赖 Proma 既有的 will-navigate / window.open 拦截，不新造安全声明 | 遵守 §9 安全边界：不写安装目录；安全口径如实、不过度承诺 |
| D5 | 打包 | open-plan 全量（server/ + client/dist + bin/ 二进制 + node_modules 闭包）进 extraResources；officecli/LibreDWG 按 `bin/清单.json` 随包；asarUnpack 追加 open-plan 原生/二进制条目 | 对齐 Proma 现有 pi-tui/node-pty 的 unpack 模式 |
| D6 | AGPL 合规 | 保留 Proma LICENSE 与版权声明；仓库 README 声明衍生关系；分发时提供完整源码链接；不复制 Proma 商业版内容 | AGPL-3.0 义务 |
| D7 | 版本列车 | 桌面版独立版本号 `0.19.x-guiju`（跟随 Proma 基线），与 open-plan web 版 `0.13.x` 双轨；`变更日志.md` 双仓各记 | 两基线演进节奏不同 |

## 7. 明确不做（首期）

- 不重写 open-plan 任何业务模块为 TypeScript/Proma 包结构（迁移 ≠ 重构）；
- 不替换 open-plan 的 Pi 1.5.1 内核为 Proma 内核 0.87.1；
- 不做 Proma 内核与 open-plan 内核的会话互通；
- 不迁移凭据到 safeStorage 加密（保持现有存储，P4 再评估）；
- **首期禁用 electron-updater 自动更新**（Proma 打包态会启动 updater，须显式关闭；启用与否 P4 单独拍板）；
- **不做存量数据自动迁移**：首期不搬旧工作区数据到 userData 新根，首启动引导用户重新选择工作区目录（旧目录只读引用，不复制不改动）；
- **不给 Electron main 进程加后端负载**（sidecar 既定，后端全在子进程）；
- 不做 macOS/Linux 打包（现有构建链仅 Windows）；
- 不动 Proma main 分支（保持上游镜像）。

| 风险 | 影响 | 预案 |

## 10. 对抗审查

> 审查者：独立子代理（general-purpose，与方案作者不共享上下文，只读）　日期：2026-11-21
> 结论原文如下，已修复项见 §11 修订记录；无遗留未处置项。

### 审查原文

**1. 重复造轮子 — 结论：无问题，但引用失实需更正**

Proma 壳件确实齐备可复用：单实例锁 `apps/electron/src/main/index.ts:22`、菜单/托盘 `index.ts:77-79`、对话框 IPC `main/ipc.ts:3850/6133`。preload 已有文件对话框与打开能力：`preload/index.ts:438 openFileDialog`、`:900 openFileOrFolderDialog`、`:950 openFile`、`:971 showItemInFolder`——但 D3 写的「openPath/showOpenDialog 等 API 名」与实际暴露名不符（能力在、名字不对）。
证据：方案 §2.2 引用 `desktop/server/服务入口.mjs`——该路径不存在，真实文件在 `server/服务入口.mjs`（glob 验证），方案全文路径错误。
修复建议：更正引用路径与 API 名；其余复用判断成立。

**2. 遗漏边界 — 结论：有问题（最严重）**

证据：`server/index.mjs:7970-7972` 注册 `process.on("uncaughtException")` → `shutdownService` → `:7965 process.exit(1)`，注释明言「由启动脚本的监督循环拉起干净进程」。方案 D2 把 server 进程内 import 进 Proma main 后：**server 任何未捕获异常 = 整个 Electron 壳退出，且 fork 仓库没有 服务监督.mjs，无人拉起**。§8 只备了「import 失败切 sidecar」，运行期崩溃边界完全没写。另外 `:7976` 全局吞 unhandledRejection、`:7983` 叠加 exit 落盘，均会改变 Proma main 的既有行为。
次级问题：①「一次性 token」名不副实——`服务入口.mjs:62` 每次启动一枚、全程有效（`index.mjs:8000` 明示 `/?token=` 进 UI）；Proma 已有 will-navigate/window.open 拦截（`index.ts:623-644`）缓解外泄，方案应写「继承现状」而非新造声明。②`desktop/src/main.cjs:134-150` 的 `browser:setBounds/setVisible` WebContentsView 宿主是 server 侧 browser_* 工具的依赖，D3 平台桥只覆盖 client 侧，P2/P3 无迁移任务。③Proma main 以 CJS 打包（`apps/electron/package.json:18`），open-plan 有 6 个 server 文件用 `import.meta`（goal.mjs、kb.mjs 等）——静态 import 会被 esbuild 吞进 CJS 而炸，方案未写「open-plan server 必须 esbuild external / 动态路径 import」。
修复建议：补「server 崩溃→壳降级/重启」边界方案与 esbuild external 约束。

**3. 冲突 — 结论：有问题**

证据：ADR 0024 明确「版本继续 0.13.x 补丁线，桌面端首发 v0.13.25」（`docs/决策记录/0024-….md:56`），D7 的 `0.19.x-guiju` 实质废止该条款，但 P0 任务清单无「补 ADR/废止 0024 版本条款」；AGENTS.md §4.3 要求桌面壳变更留决策记录。另外 P0 任务 3「业务继续在 develop」与 §9.3「P1 后开发主线整体切 fork」矛盾——fork 仓库里 AGENTS.md/规范/ADR/verify 门禁如何治理未交代。fork 根 `package.json:39-44` 把 pi-\* overrides 锁 0.87.1、workspaces 仅 `packages/*`+`apps/*`（`:7-9`），方案未写明「open-plan/ 不进 workspaces、不参与 bun install」的防误操作约定。
修复建议：P0 增补 ADR 任务与 fork 治理方案（宪法/规范/门禁随树迁移的口径）。

**4. 不可行假设 — 结论：有问题**

证据：「Electron 43 内置 Node 22.x」无本地证据——fork 无 node_modules、无 .nvmrc、README 无 node 字样；真正的硬约束是 pi SDK `engines.node >=22.19.0`（`node_modules/@earendil-works/pi-coding-agent/package.json:94-96`）。若 Electron 43 内置 Node < 22.19 或已跳 24，D2 失败。且「与 open-plan engines 对齐」是虚的：open-plan `package.json:1-339` **根本没有 engines 字段**。利好事实：open-plan 直接依赖（`package.json:314-334`）无原生编译模块，pi 依赖均为 JS/WASM——ABI 风险比方案渲染的低。`服务入口.mjs:18-20` 仅 import node 内置模块，纯 Node 可跑、无 Electron 依赖——D2 本身技术成立。
修复建议：P0 增加「Electron 43 实测 process.versions.node ≥ 22.19」前置验证，删除 engines 对齐表述。

**5. 测试缺口 — 结论：有问题**

证据：P1 任务 1 迁入清单只列「client/ + server/ + package.json + bin 清单」（方案 ：92），**不含 scripts/**——但 verify 与全部 test:\* 都在 scripts/（`package.json:38-312`），Review 模式还依赖 docs/规范；P1 验收却要求「verify 全绿」（:101），清单与验收自相矛盾。嵌套 npm install（open-plan 用 npm）在 Bun monorepo 内的行为、electron-builder extraResources 闭包打包均未验证。P3 五批无批量工时与入口条件，批 D 内嵌「前置决策」却无进入门槛。崩溃边界（第 2 项）无任何测试口径。
修复建议：P1 清单补 scripts/ + docs/，P0 加「fork 内 npm install + verify 试跑」任务。

**6. 范围与不做清单 — 结论：存疑**

证据：不做清单漏三项有据可查的关键项：①自动更新——Proma 在 isPackaged 时启动 electron-updater（`index.ts:815-818`），迁移后与 open-plan renderer 的关系必须显式决策（哪怕写「首期禁用」）；②性能预算——ADR 0024:63 已记录「主进程承载后端、重任务需移出主线程」的负面后果，方案无对应任务；③存量用户数据向 userData 新根的迁移/兼容。P3 批 D（地图+画布+浏览器三个最重域）单批过重。
修复建议：不做清单补齐三项；批 D 拆分或给入口条件。

**总体结论**：方案骨架方向正确（复用 Proma 壳件、服务入口链路同构、分阶段），但按 §7.3 标准，当前版本不得直接提交用户确认，须先修订 4 个硬伤：进程内崩溃边界、P1 迁移清单与 verify 验收矛盾、Electron 43 内置 Node 版本未验证、ADR 缺位。另需顺带更正：服务入口.mjs 引用路径、D3 API 名、「一次性 token」措辞、esbuild external 约束、不做清单补自动更新/性能预算/数据迁移。修订并复审后即可提交确认。
